# Отчет по выполнению задачи: Spring Security «Безопасное приложение»

## 1. Цель работы
Реализовать базовую настройку безопасности для существующего Spring Boot приложения с использованием Spring Security. Ограничить доступ к endpoint'ам: настроить стандартную форму логина от Spring, сделать как минимум один endpoint публичным (доступным без авторизации), а остальные — защищенными (требующими обязательной аутентификации).

## 2. Использованные технологии и инструменты
* **ОС:** Windows 10
* **Среда разработки:** IntelliJ IDEA Community Edition 2025
* **Язык программирования:** Java 17 (OpenJDK 17.0.6_10)
* **Сборщик проектов:** Apache Maven
* **Фреймворк:** Spring Boot 2.7.18
* **Зависимости:** 
  * `spring-boot-starter-web` — для создания REST-контроллера
  * `spring-boot-starter-security` — для интеграции механизмов безопасности
  * `spring-boot-starter-validation` — для валидации входных данных
* **Инструменты тестирования:** Браузер (для проверки редиректов на страницу логина и работы стандартной формы), Postman / cURL (для тестирования REST API и POST-запросов)

## 3. Выполненные шаги
### 3.1. Добавление зависимости Spring Security
В файл `pom.xml` добавлена стартовая зависимость:
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

### 3.2. Исправление несовместимостей в существующем коде
Для корректной работы приложения на Spring Boot 2.7.18 потребовалось внести правки в классы `Person` и `MyDevController` 

### 3.3. Добавление новых endpoint'ов в контроллер
В класс `MyDevController` добавлены два новых метода для наглядной демонстрации работы безопасности:
* `@GetMapping("/public")` — публичный endpoint.
* `@GetMapping("/private")` — защищенный endpoint.

### 3.4. Создание конфигурации безопасности
Создан класс `SecurityConfig` в пакете `config`, который наследуется от `WebSecurityConfigurerAdapter` (согласно требованию задания).
Переопределен метод `configure(HttpSecurity http)`:
* Отключена CSRF-защита (`.csrf().disable()`) для удобства тестирования API.
* Настроены права доступа: `.antMatchers("/public", "/hello").permitAll()` (разрешен анонимный доступ) и `.anyRequest().authenticated()` (остальные требуют авторизации).
* Включена стандартная форма входа: `.formLogin()`.

### 3.5. Тестирование приложения
* Запуск приложения и копирование автоматически сгенерированного пароля из консоли (пользователь по умолчанию — `user`).
* Проверка доступа к публичным и приватным ресурсам до и после аутентификации.

## 4. Проблемы и их решения
### Проблема 1: Ошибки компиляции в классе `Person.java` (отсутствует пакет `jakarta.validation`)
* **Причина:** В исходном коде использовались импорты `jakarta.validation.constraints.*`, которые являются стандартом Jakarta EE (применяется в Spring Boot 3.x и выше). Однако проект использует Spring Boot 2.7.18, который базируется на Java EE (`javax.*`).
* **Решение:** Замена всех импортов `jakarta.validation.*` на `javax.validation.*` в классе `Person.java`.

### Проблема 2: Endpoint `/hello` не обрабатывает POST-запросы (ошибка 405 Method Not Allowed)
* **Причина:** Метод `hello` в классе `MyDevController` имел модификатор доступа `private`. Spring MVC не может вызвать приватный метод через механизм (reflection) для обработки HTTP-запроса.
* **Решение:** Изменение модификатора доступа метода `hello` с `private` на `public`.

## 5. Чек-лист самопроверки
- В `pom.xml` добавлена зависимость `spring-boot-starter-security`.
- Создан класс-наследник `WebSecurityConfigurerAdapter`.
- Настроена стандартная форма логина (`.formLogin()`).
- Как минимум один endpoint (`/public`) доступен без авторизации.
- Все остальные endpoint'ы (`/private`) требуют обязательной авторизации.
- При попытке доступа к защищенному ресурсу происходит редирект на `/login`.
- Успешный вход с использованием дефолтного пользователя `user` и пароля из консоли.
- Код компилируется без ошибок (учтены различия `javax` и `jakarta`).

## 6. Полученные результаты
**Поведение приложения до авторизации:**
* `GET /public` → `Это публичные данные! Авторизация не требуется.` (HTTP 200)
* `POST /hello` → `Hello from myAppTest to name ...` (HTTP 200, работает без токенов)
* `GET /private` → Автоматический редирект (HTTP 302) на стандартную страницу `http://localhost:8088/login`.

**Поведение приложения после успешной авторизации:**
* Ввод логина `user` и пароля из консоли.
* `GET /private` → `Это закрытые данные! Доступ разрешен только после авторизации.` (HTTP 200).

**Архитектурные итоги:**
* Настроен декларативный контроль доступа к ресурсам на основе URL-шаблонов (`antMatchers`).
* Реализована прозрачная для пользователя форма аутентификации.
* Разделены публичные и приватные зоны REST-приложения.

## 7. Вывод
В ходе выполнения домашней работы были освоены базовые, но критически важные механизмы обеспечения безопасности в Spring Boot. 
Главными достижениями являются:
1. **Интеграция Spring Security:** Успешное подключение стартера и переопределение стандартных настроек безопасности через наследника `WebSecurityConfigurerAdapter`.
2. **Гранулярная настройка доступа:** Научился разграничивать права доступа к endpoint'ам с помощью `HttpSecurity.authorizeRequests()`, выделяя публичные (`permitAll`) и защищенные (`authenticated`) зоны.
3. **Работа с особенностями версий Spring Boot:** На практике закреплено понимание различий между пакетами `javax.*` (Spring Boot 2.x) и `jakarta.*` (Spring Boot 3.x), что позволило избежать ошибок компиляции.
4. **Понимание HTTP-безопасности:** Разобран механизм работы CSRF-защиты и правила формирования доступных для Spring MVC контроллер-методов (модификатор `public`).

Реализованное приложение полностью соответствует требованиям задания: оно использует стандартную форму логина, имеет публичные и защищенные маршруты, а код конфигурации безопасности инкапсулирован в отдельном классе `SecurityConfig`.
